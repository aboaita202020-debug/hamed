# HAMED AI — REVENUE OS & AUTONOMOUS EXECUTION SPECIFICATION

Version: 1.0
Status: Mandatory implementation specification
Relationship: Extension of `HAMED_AI_MASTER.md`

## 1. Objective

Hamed AI must implement a Revenue Operating System that continuously discovers, validates, launches, measures, optimizes, and scales legitimate revenue opportunities for the owner and for customers using Hamed as a service.

The target is not guaranteed income. The system must optimize for **realized revenue, verified profit, customer value, retention, and sustainable growth**. Never fabricate revenue or claim a transaction happened without a confirmed result.

Hamed should execute autonomously within configured permissions. It must not repeatedly ask the owner for routine low-risk decisions. High-impact financial commitments, money transfers, binding contracts, irreversible actions, security changes, regulated activities, and other protected actions remain behind server-side approval gates.

## 3. Revenue multiplier

Every successful revenue source must be evaluated for conversion into a larger portfolio:

ONE-OFF DEAL → SUBSCRIPTION → REFERRAL/AFFILIATE → MARKETPLACE → API → WHITE-LABEL → ENTERPRISE

Hamed should automatically identify which expansion paths are technically and commercially appropriate, then test them in controlled experiments.

## 4. Revenue OS modules

Mandatory architecture:

1. Revenue Registry — every monetization channel, product, price, owner, status, and economics.
2. Opportunity Scanner — continuously discovers opportunities.
3. Demand Validator — tests whether real demand exists.
4. Pricing Engine — recommends prices using evidence and unit economics.
5. Experiment Engine — runs controlled commercial tests.
6. Customer Acquisition Engine — finds compliant acquisition channels.
7. Conversion Engine — improves offers, funnels, follow-up, and messaging.
8. Billing Engine — subscriptions, usage, invoices, commissions, and entitlements.
9. Affiliate/Partner Manager — tracks partner agreements and attribution.
10. Marketplace Transaction Engine — matching, transactions, fees, and status.
11. Outcome Measurement — records realized revenue, cost, profit, retention, refunds, and satisfaction.
12. Revenue Attribution — connects revenue to source, agent, campaign, offer, partner, and experiment.
13. Fraud/Abuse Guard — detects suspicious transactions, fake leads, duplicate events, abuse, and manipulation.
14. Compliance/Consent Engine — checks applicable permissions, disclosures, opt-outs, and policy constraints.
15. P&L / Unit Economics — revenue, gross profit, contribution margin, CAC, payback, refunds, and verified ROI where inputs permit.
16. Portfolio Optimizer — allocates attention to high-value opportunities.
17. Auto-Scale / Kill Engine — scales proven winners and stops persistently poor experiments.
18. Daily Revenue Mission — tracks target, pipeline, realized revenue, and gap-to-target.
19. Approval Router — server-side authorization for consequential actions.
20. Audit Log — immutable/append-only records where practical.

## 5. Opportunity scoring

Each opportunity must contain:
- opportunity_id
- source
- customer/target
- problem
- solution
- evidence
- expected_revenue
- expected_cost
- expected_profit
- probability
- expected_value
- time_required
- cash_required
- customer_value
- risk_score
- confidence_score
- strategic_value
- learning_value
- approval_required
- next_action
- status

Base calculation:
`expected_value = expected_profit × probability_of_success`

Ranking must be configurable and must consider expected value, time, risk, strategic value, customer value, and learning value.

## 6. Autonomous commercial loop

Hamed must operate this loop continuously:

OBSERVE → DISCOVER → VERIFY → UNDERSTAND → SCORE → PLAN → DECIDE → ACT → VERIFY RESULT → MEASURE → LEARN → OPTIMIZE → REPEAT

If critical evidence is missing, Hamed must WAIT or gather more evidence instead of hallucinating.

## 7. Customer acquisition requirements

Hamed must be able to discover qualified prospects from lawful public sources and authorized integrations. For each prospect:

1. Research business.
2. Identify a likely problem.
3. Verify the problem where possible.
4. Select an appropriate offer.
5. Estimate business value.
6. Create personalized outreach.
7. Contact only through permitted channels and applicable consent rules.
8. Track reply/interest.
9. Qualify.
10. Follow up appropriately.
11. Convert or close.
12. Record outcome.

No spam campaigns, fake identities, fake scarcity, fake reviews, deceptive claims, or platform abuse.

## 8. Customer psychology requirements

Hamed should learn customer decision factors including needs, motivations, pain points, risk, trust, value perception, friction, objections, decision stage, and satisfaction.

It must not use protected-trait profiling or manipulative tactics designed to cause harmful or unsuitable purchases.

## 9. Learning and experimentation

Hamed must learn from:
- Its own verified commercial outcomes.
- Public lawful sources.
- Public research and case studies.
- User-provided material.
- Licensed or public-domain books/materials.

Learning pipeline:

LEARN → EXTRACT → VERIFY → CLASSIFY → PRACTICE → TEST → MEASURE → REFLECT → UPDATE PLAYBOOK

Each strategy stores source, date, evidence quality, domain, use cases, contraindications, confidence, test plan, outcome, and version.

## 10. Cost-aware AI operation

Hamed must not depend on a single model provider. Implement a provider abstraction and model router with:
- capability routing
- confidence routing
- cost routing
- latency routing
- fallback
- rate-limit handling
- retry/backoff
- circuit breaker
- health checks

Possible providers may include OpenAI, Claude, Gemini, DeepSeek, Kimi, or other configured providers. Credentials remain outside source control.

If a provider is unavailable or rate-limited, Hamed should automatically use a healthy configured fallback where permitted rather than failing the entire mission.

## 13. Implementation mandate

This document is a **required implementation backlog**, not merely an idea list.

Codex/developers implementing Hamed must:

1. Inspect the current repository architecture before modifying it.
2. Preserve working features.
3. Implement the Revenue OS modules incrementally.
4. Add configuration and database models for revenue opportunities, experiments, customers, partners, transactions, subscriptions, attribution, and audit events.
5. Add APIs/services/tools for each implemented module.
6. Add specialist agents behind the common orchestrator.
7. Add automated tests for every new critical module.
8. Add integration tests for revenue workflows.
9. Add failure tests for model rate limits, missing data, tool failures, duplicate events, and unauthorized actions.
10. Add approval tests proving protected actions cannot bypass server-side authorization.
11. Add observability: structured logs, metrics, health checks, and error reporting.
12. Update `.env.example`, documentation, and deployment configuration.
13. Keep paid providers optional wherever a functional free/local alternative is possible.
14. Never hard-code API keys or credentials.
15. Never claim implementation is complete unless the corresponding code and tests exist.
16. Run the full test suite before deployment.
17. Fix failures before release.
18. Verify health endpoints and startup behavior.
19. Verify Telegram and other enabled channels independently.
20. Verify that the application can continue operating when the owner's device is offline, provided cloud/hosting and required provider integrations are available.

## 16. Final operating rule

Hamed's commercial intelligence should always ask:

**What legitimate problem can I solve? Who has that problem? What evidence proves it? What is the customer value? What is the unit economics? What is the lowest-risk next action? Can I execute it autonomously within permission? How will I verify the result? Can the successful workflow become recurring, scalable, licensed, API-based, marketplace-based, or enterprise revenue?**

The answer must drive execution through the orchestrator, not remain as a chat suggestion.
